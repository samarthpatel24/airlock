Seal online. Carry it across. Verify offline.

  1. Seal

    Online · airlock seal

    • Refuses formats that can run code when loaded, like pickle.
    • Matches every file to a pinned Hugging Face commit.
    • Signs a manifest of every file and its SHA-256 with cosign.
    Car 1

  2. Move

    Air gap · Zarf or USB

    • The bundle travels on its own. airlock does not ride this car.
    • Anything that changes a byte on the way shows up at the next stop.
    Car 2

  3. Verify

    Offline · airlock verify

    • Checks the signature before it reads the manifest.
    • Every file must match: none missing, extra or changed.
    • Writes a Markdown report for the security team, pass or fail.
    Car 3

  • Pickle files

    Formats that can run code when loaded never get sealed.

    "pytorch_model.bin": pickle-based format refused: it can execute code when loaded; convert to safetensors or GGUF Refused

  • An untrusted key

    A bundle signed by any key the offline host does not hold.

    invalid signature (wrong key or tampered) Refused

  • Weights from the wrong commit

    Every file must match the pinned upstream commit. Branch names are refused because they can move.

    "model.gguf": sha256 differs from upstream Refused

  • A swapped or poisoned model

    The demo's poisoned copy tells users to pipe a script into sudo sh. One changed byte after sealing, and the hash no longer matches.

Gate

Zarf moves the boxes

Zarf's signature proves the package is the one the packager built. It does not prove what went into it. A model swapped before packaging passes Zarf's checks.

airlock runs as a deploy step inside the package. It checks the model against its own seal, made earlier from the real files, so the swap is refused and the model server never starts.

Always sign the package and deploy with --verify=always. Tested with Zarf v1.0.0.

End of the line

What airlock does not cover, so you can plan for it.

A stolen signing key
Keep cosign.key off shared machines and rotate through a trusted channel.
Harmful model behaviour
A safe format from the right commit can still be a bad model. Outputs are not evaluated.
Changes after verification
Running verify during the Zarf deploy keeps that window small.
A malicious upstream commit
Pinning stops later changes, not a bad commit.
Rollback
An older bundle signed by the same key still verifies.
Chat templates
Not inspected. Render them in a sandboxed loader.
Metadata values and tensor bytes
Read but not judged.
A compromised online machine
Seal trusts the machine it runs on.
Small upstream files
Matched by git SHA-1, since that is all Hugging Face publishes for them.
Transparency logs
Key-based signatures only, because air-gapped sites rarely reach Rekor.
The serving image
Scan it with Zarf's SBOMs or a scanner.
